# 性能与容量实测

R16 各指标的实测值与测量方法。测量时间 2026-11-22，设备 Intel Core i5-14400（16 逻辑核）/ 32 GB / Windows 11 / Node.js 22.19.0 / Electron 33.4.11 / 构建产物（非 dev 模式）。

## 一、引擎基准（30 天 × 5 万条采样）

由 `tests/perf/bench.test.ts` 在临时目录生成 30 天数据（写入 936 ms，落盘 106.9 MB），运行 `npm test` 时打印：

| 指标 | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| 单日读取 50000 条 | — | 34–39 ms | 参考 |
| 全量 `buildDayRollup`（单日 5 万条） | — | 4.6–4.7 ms | 参考（冷启动与测试用） |
| 增量建索引（单日 5 万条） | — | 6.4–6.5 ms | 参考 |
| 新增采样到可查询（追加 + 取汇总） | ≤ 16 ms | 均摊 **7.0 µs** | 达标 |
| 切换历史日期（1 天 5 万条，含读盘） | ≤ 300 ms | **约 41 ms** | 达标 |
| 跨 7 天检索（冷，含读盘与建索引） | ≤ 800 ms | **345–516 ms** | 达标 |
| 跨 7 天检索（热，走缓存） | ≤ 5 ms | **0.3–0.5 ms** | 达标 |
| 堆占用（LRU 驻留 8 天） | ≤ 300 MB | **66–68 MB** | 达标 |

冷检索的两次实测分别是 345 ms 与 516 ms，差异来自文件系统缓存与后台负载；两次都低于 800 ms。热检索是界面实际调用路径（同一会话内重复检索）。

## 二、应用级指标（真实构建产物）

用 `node scripts/probe-metrics.mjs [秒数] [--hidden]` 测量：启动到首帧可交互取"进程启动 → 连续两帧 rAF"；CPU 取所有 electron 进程 `TotalProcessorTime` 增量除以墙钟与核数；内存取 `WorkingSet64` 之和。

| 指标 | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| 冷启动到可交互 | ≤ 2.0 s | **630–930 ms** | 达标 |
| 空闲 CPU（窗口收进托盘，60 秒窗口） | ≤ 0.5%（整机 16 核） | **0.13%**（单核 0.8%） | 达标 |
| 常驻内存 RSS（窗口收进托盘） | ≤ 300 MB | **249–254 MB** | 达标 |
| 回放时帧率（mock 200 镜头，600x） | ≥ 50 fps（参考） | **中位 60 fps，p5 56 fps** | 达标 |

参考值（窗口打开、界面可见）：空闲 CPU 0.9%（整机），RSS 341 MB，electron 进程 4 个（多出渲染进程与 GPU 进程）。

测量窗口为 20 秒时会读到 0.67–0.9% 的空闲 CPU，其中包含启动后的收尾工作；改用 60 秒窗口即回落到 0.13%。以 60 秒窗口为准。

## 三、测量方法与复现

```powershell
npm test                                  # 引擎基准数字打印在 stdout
node scripts/probe-metrics.mjs 60 --hidden   # 常驻口径：启动、空闲 CPU、RSS
node scripts/probe-metrics.mjs 20            # 可见口径（参考值）
npx electron scripts/probe-mock.cjs out.png 1280 820   # 版式、帧率
```

## 四、已知限制

- 帧率在 mock 数据（约 200 个镜头、600x 回放）下测得，真实单日通常更稀疏，负载只会更低。
- RSS 是 4 个进程（可见）或 3 个进程（收进托盘，GPU 进程退出）之和；Electron 自带 Chromium 的固定开销决定了下限，60–90 MB 的优化空间需要裁剪 Chromium 特性，收益与风险不匹配。
- 冷检索对磁盘状态敏感，机械硬盘或冷启动后的首次读盘会更慢。
