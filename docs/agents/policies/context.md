# 上下文管理规范

从项目入口开始，按任务和实际影响查阅必要规则、项目知识与工程证据。查阅范围以正确执行和验证任务所需的信息为准。

## 执行前

1. **确认入口。** 从 [AGENTS.md](../../../AGENTS.md) 确认适用的启动规则，通过 [Agent 规则索引](../INDEX.md) 定位适用规范。需要定位项目知识时，从[项目文档索引](../../INDEX.md)进入相关目录，再按局部索引查找文档。已知适用的权威文档路径时，直接查阅对应文档。需要项目概况或启动方式时，查阅[项目 README](../../../README.md)。
2. **按任务类型选流程。** 根据目标和完成条件选择适用的工作流。例如，新增功能采用功能开发流程，修复异常采用缺陷修复流程。
3. **按影响范围找资料。** 根据预计受影响的模块、接口、数据和用户行为，确定需要核对的 Policy、规格、契约、代码和测试。涉及领域术语或重大架构决策时，通过[领域文档](../domain.md)定位术语表和相关 ADR。
4. **补齐两条路径发现的必要依赖。** 核对工作流要求的资料，以及预计受影响范围内的关键约束。开始执行前，确认完成条件、预计影响范围和仍待核实的关键事项。

### 判断哪些资料必读

- **必要依赖。** 缺少这项信息就无法正确实现、审查或验证当前任务。先补齐理解它所需的前置资料，再查阅对应内容。条件成立时，把对应的条件依赖纳入必读范围。
- **相关资料。** 需要补充背景或解释某个具体问题时再查阅。代码、测试或接口证据表明某项资料会影响关键判断时，将它纳入必要依赖。

## 发现影响变化时

用相关代码依赖、调用方、接口变更、测试结果和现有自动化检查核对影响范围。发现新影响时，在继续受影响的工作前补查相应的规则、契约、代码和验证要求。

例如，修复某个 Operation 的返回结果时，先核对缺陷描述、相关实现和测试。如果问题追溯到 `OperationEngine` 的执行协议，再查阅相关协议、适用的 ADR、受影响的调用方和引擎测试。

## 资料缺失或冲突

1. **核对来源。** 确认各来源的权责、适用范围、生效状态和替代关系。正式规格在仓库外时，按项目索引记录的位置和检索方式获取。
2. **区分预期与实际。** 用正式规格确认应有行为，用代码、测试和运行结果核对实际行为。两者冲突时，查明是需求变化、实现缺陷还是文档过时，再按仍然生效且适用的规则处理。
3. **说明关键缺口。** 必要来源缺失、无法访问或冲突仍影响关键判断时，说明缺失或冲突的依据，以及哪项判断受影响。以核实的现行来源补齐缺口。判断是否暂停、请用户决策或继续其他工作时，查阅[人类注意力规范](attention.md)。

## 交付前

根据实际改动或审查范围，核对适用的契约、验证要求和文档影响。新增影响触发了必要依赖时，补查后再做受影响的验证或判断。

当所有已识别的关键约束和必要依赖均已核对，且影响执行或交付的重大冲突均已解决时，结束上下文查阅。

## 在索引和工作流中记录依赖

- **索引。** 写明资料讲什么、权威来源在哪里、何时查阅，以及有哪些必要前置和条件依赖。将必要依赖与相关资料标明。
- **工作流。** 开头写明适用条件、该类任务的基础依赖，以及哪些影响会触发额外必读资料。通过链接指向权威规则和项目知识。
