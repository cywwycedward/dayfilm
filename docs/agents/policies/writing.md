# 文档编写与修改规范

新增、修订、整理或重构项目文档、代码注释和 Docstring 时，交付一份可独立理解和使用的说明，准确反映当前有效的设计与实现。

## 编写与修改步骤

1. **确定目标。** 明确读者读完后要理解什么、能完成什么。标出现有内容中应保留、替换、删除或补充的部分。
2. **确认影响范围。** 找齐受影响的章节、标题、目录、术语、示例、交叉引用及相关的代码注释和 Docstring。保留范围之外仍然正确且必要的内容。
3. **直接改成目标状态。** 删除或替换失效内容，合并重复说明，按需要拆分、移动或重写段落和示例。正文直接呈现现行规则和用法。需要留存的修改缘由和过程记在版本历史、迁移记录等专门位置。兼容、过渡、备用规则和例外只保留当前用法确需说明的部分。
4. **核对技术事实。** 按文档用途区分已确定的设计和实际行为。对照可核实的实现、接口、配置、测试和相关文档，确认技术行为、约束、默认值和示例都有依据。核实并消除与本次修改直接相关的矛盾。仍影响理解或使用的未知项，明确写出待核实的事项。
5. **通读成稿。** 从首次阅读的角度检查读者是否具备理解和使用所需的信息，相关事实、名称、命令、示例和链接是否一致，行文是否自然。清理重复、补丁式说明和无关铺垫后再交付。

假设测试入口已从 `npm test` 改为 `pnpm test`，直接将正文改为“运行 `pnpm test` 执行测试。”

## 组织文档

- 按读者理解和使用的顺序写。先说明对象或目的，再交代前置条件、操作、结果和关键限制。概念、步骤和参考信息分别呈现。
- 根据文档类型写齐会影响理解或使用的信息，例如适用范围、关键行为、输入输出、默认值、边界条件和失败情形。明确写出必要的限制及其适用条件。
- 简单内容直接说明。内容复杂时，用小节、列表、表格或示例帮助读者定位。沿用项目的格式、链接和标题层级约定。
- 同一概念的完整说明集中在一处。其他位置用简短引用或链接，保持相关文档中的含义一致。正文、标题、目录和交叉引用一起核对。
- 正文写明影响使用的规则，示例用来演示已说明的行为。按现行接口、命令和约定核对示例的名称、路径、参数及预期结果。

## 使用中文和术语

- 默认用自然中文，按中文技术交流的习惯写清动作、对象和结果。用“更新配置”这样直接的表达，依据实际技术含义选词。
- 沿用项目术语。常见且准确的中文技术术语优先用中文，代码标识符、命令、文件名、字段名、协议名和需要精确对应的 API 名称保留原文。
- 按技术机制选译法。`fallback` 可指备用方案、回退处理或降级处理，按实际语境选用。文档内同一概念称呼一致，生僻术语按需在首次出现时简释。
- 直接陈述事实、规则和条件。只有强调会帮助读者阅读或操作时才使用突出格式或“注意”“重要”等提示。删去显而易见的解释、同义反复、无关免责声明和含混限定词。

## 编写代码注释和 Docstring

- **代码注释。** 解释从代码本身难以看出的设计意图、前提、非直观行为或取舍。相关逻辑变化时，直接更新或删除已失效的注释。
- **Docstring。** 按接口复杂度说明用途和必要的契约信息，包括参数、返回值、异常、副作用和使用限制。名称、类型、默认值和实际行为与代码一致。函数名和类型定义已经清楚表达的信息可省略。
- **语言与格式。** 遵循项目现行的注释语言以及 Docstring 风格和结构约定。中文表述采用自然中文，代码标识符保留原始拼写。
