# 重构工作流

## 适用条件

调整代码结构，同时保持调用方依赖的既有行为。目标涉及已确认行为的改变时，使用[功能开发工作流](feature.md)。发现需要修复的现有偏差时，按[缺陷修复工作流](bugfix.md)确定原因和验证方式。

## 上下文依赖

核对受影响的实现、调用点、契约和现有测试。[工程文档索引](../../engineering/INDEX.md)

- 调整模块职责或依赖方向时，补查架构及相关决策。[架构文档索引](../../architecture/INDEX.md) · [领域文档](../domain.md)
- 重组接口实现、数据访问或配置读取时，补查调用约束和兼容要求。[API 与接口契约索引](../../api/INDEX.md) · [数据文档索引](../../data/INDEX.md)

## 执行步骤

1. **说明结构问题和预期收益。** 结合真实调用点说明重复维护、职责分散或依赖造成的具体问题。需要重新判断模块职责或接口时，可用 `codebase-design`。复杂的跨模块调整可用 `architecture-design` 梳理依赖和生命周期。
2. **建立行为基线。** 从调用方视角列出受影响的输入输出、错误、状态顺序和副作用。用现有关键场景记录重构前的结果，影响验收的覆盖缺口按需补证。
3. **小步调整并验证。** 按可以独立验证的步骤调整结构。复用同一组可观察行为对照前后结果，按影响补查调用方和集成场景。例如，重组取消逻辑时，按受影响范围分别检查排队、运行和收尾阶段的行为。[引擎行为测试](../../../tests/test_engine.py)
4. **检查文档影响。** 核对实际调整是否改变长期架构说明、开发约定或其他持久知识。[项目文档治理规范](../policies/documentation.md)

## 完成条件

结构收益可以定位到具体职责、依赖关系或调用路径。受影响的既有行为有可对照的前后证据，验证缺口及文档影响已交代。
