# 功能开发工作流

## 适用条件

新增功能或改变已确认的功能行为。恢复已确认的行为时，使用[缺陷修复工作流](bugfix.md)。

## 上下文依赖

开始前核对已确认的需求和验收条件、适用的开发约定、相关实现及测试。[功能规格索引](../../specs/INDEX.md) · [工程文档索引](../../engineering/INDEX.md)

| 影响 | 补查的资料 |
| --- | --- |
| 新增或变更公开 Operation 或其他公共接口 | 核对调用方、注册方式、输入输出、错误和执行策略。 [API 与接口契约索引](../../api/INDEX.md) |
| 改变持久化数据或配置 | 核对数据约束、现有数据的兼容性和迁移要求。 [数据文档索引](../../data/INDEX.md) |
| 涉及跨模块职责、依赖方向、线程边界或生命周期 | 核对现有架构和相关决策。可用 `architecture-design` 梳理边界和交互，需要图时用 `archify`。 [架构设计](../../architecture/INDEX.md#架构设计) · [领域文档](../domain.md) |

## 执行步骤

1. **明确验收条件。** 说明用户或调用方能观察到的变化，列出适用的输入、结果和关键失败情形。验收条件应能通过正常使用路径核对。
2. **先确定技术方案和架构。** 根据需求和现状，明确沿用或调整的模块职责、调用接口、数据和状态流转、关键限制及验证入口。验证状态设计时可用 `prototype`，设计界面时可用 `impeccable`，并将结论纳入方案。存在实质性设计取舍时，按规范判断是否需要用户决定。方案和架构确定后再拆分和正式实现。局部功能可以简述方案后直接进入实现。[人类注意力规范](../policies/attention.md)
3. **按可独立验收的功能点拆分。** 内容较多时，将方案拆成较小的端到端功能点。例如，两个可独立使用的 Operation 可以分别贯通注册、调用和验证。每项明确可观察的结果、验收方式、前置依赖和改动范围。
4. **按依赖委派。** 拆分后，主 Agent 将接口已确定、写入范围互不重叠的功能点委派给不同 Agent 并行实现。有前置依赖的按顺序推进，共享文件由一人负责。派发时交代已经确定的方案、起始版本、写入范围和验收条件。并行写入使用独立 worktree 或等效隔离。[多 Agent 协作规范](../policies/collaboration.md)
5. **按方案实现和验证。** 每个实现者从正常入口验证自己负责的功能，交付改动版本和验收证据。需要改变公共契约或模块边界时，先由主 Agent 协调确认方案变更，再继续受影响的实现。
6. **集成并验收。** 主 Agent 核对各项结果、适用的评审结论和集成条件。在目标工作区逐项验证原验收条件、跨功能点的组合行为和受影响的既有行为，并处理文档影响。[项目文档治理规范](../policies/documentation.md)

用户明确调用相应 Skill 时，按委托选择 `to-spec` 发布规格、`to-tickets` 拆票、`wayfinder` 规划跨会话任务，或用 `implement`、`implement-spec` 按既有规格实施。按实际委托处理 Issue、分支和提交。[Issue 跟踪配置](../issue-tracker.md)

## 完成条件

实现与已确认的方案及架构一致。原验收条件逐项通过，受影响的既有行为有相应验证，文档影响已处理。仍有验收项失败或缺少证据时，逐项说明实际结果、缺口及影响。
