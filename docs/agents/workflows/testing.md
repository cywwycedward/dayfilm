# 测试工作流

## 适用条件

测试设计、补充覆盖、专项验收或排查不稳定用例是主要交付目标。功能开发、缺陷修复和重构中的常规验证由相应工作流完成。

## 上下文依赖

核对目标行为、验收条件或接口约束，以及现有用例、夹具、测试入口和结果判据。涉及特定 Windows 版本、采集脚本或运行配置时，补查实际测试环境。[功能规格索引](../../specs/INDEX.md) · [工程文档索引](../../engineering/INDEX.md)

## 执行步骤

1. **确定要观察的行为和判据。** 说明测试要识别哪种错误，以及通过什么入口和结果观察它。用规格、已知结果或独立推导确定预期。
2. **选择足以观察目标行为的验证环境。** 优先复用现有场景、测试数据和替身。`npm run typecheck` 覆盖静态检查，行为测试用 `npm test`（vitest），验收入口用 `scripts/` 下的探针。需要核对真实 IPC、采集子进程或打包产物时，先核对应有用例的覆盖范围，再按需启动对应探针（`probe-app.mjs` 读真实 IPC 并截图，`probe-packaged.mjs` 验打包产物）。验收窗口交互与托盘行为时，可用 `agent-desktop` 取得实际界面证据。
3. **核验判据并运行测试。** 新增或修改用例时，用已知反例、修复前失败或其他证据核对用例能识别目标错误。测试先行时，可用 `tdd` 在已约定的行为边界逐项验证用例先失败、实现后通过。先运行目标用例，再按影响范围运行相关回归。
4. **判读结果。** 区分产品失败、环境问题、跳过和未运行。探针退出码为 `0` 时，仍需核对相关检查的逐项结果。

## 完成条件

目标行为、测试入口和判据可以对应。交付可定位的命令、版本、环境和结果，说明新增覆盖、实际执行范围以及仍缺的证据。
