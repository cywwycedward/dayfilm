# 缺陷修复工作流

## 适用条件

定位或修复实际行为偏离预期的问题，包括执行异常、回归和性能退化。任务要求改变已确认的行为时，转入[功能开发工作流](feature.md)。偏差出在文档内容时，按[文档变更工作流](docs-change.md)处理。

## 上下文依赖

核对问题描述、触发条件、版本与环境、已确认的预期行为，以及相关实现和测试。规格与代码或测试冲突时，先核对来源的适用范围和生效状态。[功能规格索引](../../specs/INDEX.md) · [工程文档索引](../../engineering/INDEX.md) · [上下文管理规范](../policies/context.md#资料缺失或冲突)

发现问题涉及公共契约、任务状态、线程或工程切换时，补查相应的调用方、执行路径和相关决策。环境或 provider 会影响结果时，记录实际版本与配置。[API 与接口契约索引](../../api/INDEX.md) · [架构文档索引](../../architecture/INDEX.md) · [领域文档](../domain.md)

## 执行步骤

1. **建立可比较的基线。** 用现有失败用例、最小输入或其他可复核证据，写清实际结果与预期的差异。竞态和偶发问题记录触发时序及复现情况，性能问题固定数据、环境和指标。无法重现原场景时，说明已经观察到的现象和仍缺的条件。
2. **定位原因。** 沿实际调用路径核对故障出现的位置。疑难问题可用 `diagnosing-bugs` 缩短反馈循环，对能够解释症状的不同原因做区分性验证。例如，后台取消要区分引擎发出取消请求和 QGIS 回调确认终态两个时点。
3. **修复并对照验证。** 受托修复时，根据定位证据改动。优先用同一输入、环境和观察信号验证预期行为已恢复，再验证受影响的相邻路径。缺少能识别该回归的用例时，按影响补充行为测试。需要测试先行时可用 `tdd`。
4. **检查文档影响。** 核对受影响的使用说明、契约和排错资料，按实际影响处理。[项目文档治理规范](../policies/documentation.md)

## 完成条件

仅委托诊断时，交付症状、触发条件、有证据支持的原因判断和待核实项。委托修复时，交付修复证据及受影响路径的回归结果。原场景无法核验时，说明替代验证覆盖的行为、未覆盖的条件及其对结论的影响。
