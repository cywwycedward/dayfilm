# Dayfilm 评委 C：资源利用与 AI 深化

只回答一个问题：这份一天一天攒下来的窗口数据，还能被怎样使用，才既明显更有用、又不把 Dayfilm 变成 KPI 仪表盘。

本文只读代码与文档，未跑构建与测试；所有结论都指到函数。工作量口径沿用旧文档：S ≤ 2 天，M 3–5 天，L > 1 周。

---

## 1. 总评

1. **时间几何已经榨到九成。** `buildDayRollup()`（`src/main/reel/index.ts`）产出的镜头 / 剪辑 / 中场休息 / 时长 / 标记，被胶片脊柱、放映、周矩阵、EDL、PDF、海报、HUD 全部吃干净——一天里没有哪段"长度"信息是闲置的。
2. **标题语义只用了不到两成。** `normalizeTitle()` 与 `extractEntities()`（`src/shared/stories.ts:117,145`）只有三个下游：候选、发现、检索；没有任何函数回答"这一镜在做什么"，`judge()`（`src/main/reel/rules.ts:31`）连标题都不碰。
3. **用户自己的话浪费得最狠。** 标记（`marks.json` → `applyMarks()`）百分之百进了统计与周主线；手记（`notes.json`，每天 ≤200 字）只在它自己那一天露一次面（`renderScreenplay()`、`buildScriptHtml()`、`computePoster()` 的 `noteBlock`），从未被当成任何推理的输入，也没有任何跨天入口——写多读少的孤岛。
4. **真正没被用的不是字段，是关系。** 同一天里的**时间关系**（最长那条之后被什么接走、中场休息走了多久、回来有没有回到原地）和跨天的**同一件事**（上次停在哪），都能用纯规则从已落盘的数据里算出来，而 `findDiscoveries()`（`src/renderer/src/lib/discover.ts:162`）的四类发现一条都不算这两个。
5. **现在这条模型通道，被自己的门槛压成了装饰品。** 它只能给 1 个关键词（`MAX_TERMS = 1`）、最多 4 条（`parseStories()`），且这个词必须在真实标题里命中 ≥5 个镜头 / ≥10 分钟（`candidatesFrom()`，`src/main/ai/index.ts:154`），最后还要和 `storyCandidates()` 的规则候选合并去重（`src/main/index.ts:145-149`）——它被允许说的，几乎都是规则已经说过的话。
6. **判断：AI 在这里现在是装饰品。** 要变成必需品只有一条路：把它放到规则真的读不懂的两处——把一天写成一句带名词的人话（落进手记），把两条标题认成同一件事（归并，且必须给出双方样例）。其余一切，规则更便宜、更准、更可复现。

## 2. 数据被用到了几成

| 维度 | 现在用在哪 | 粗估 | 证据 |
| --- | --- | --- | --- |
| 时间几何（时长 / 剪辑 / 中场） | 脊柱、放映、周矩阵、EDL、PDF、海报、HUD、片场日历 | ~90% | `buildDayRollup()`、`buildWeekFilm()`、`advanceProjection()` |
| 标题 → 实体（词） | 故事线候选、四类发现、检索 | ~20% | `extractEntities()` 只被 `storyCandidates()`、`findReturn()` 用 |
| 标题 → 内容（这一镜在干什么） | 无 | 0% | 没有任何函数读标题语义；列表直接显示原文（`buildRow()`） |
| 用户标记 | 正片/花絮、周主线、剧本、统计 | ~100% | `applyMarks()`、`featureScenes()` |
| 用户手记 | 仅本日的海报 / 剧本 / PDF | ~20% | `notes.get()` 只被 `exportScreenplay()`、`exportPdf()` 调用 |
| 项目规则 | 归属、周主线、故事线矩阵 | ~60% | `matchProject()` 首命中即返回，谁吃掉了谁的镜头没人看得见 |
| 跨天同一件事 | 只有周粒度的"连续 / 换戏" | ~25% | `badgesFor()`、`buildColumns()`；没有实体级"上次出现" |

两条顺带的漂移，说明这条模型通道目前不在任何人的关键路径上：`AI_TIMEOUT_MS = 60_000`（`src/main/ai/index.ts:12`）与规格 S4.2 写的 20 秒不符；`DIGEST_LIMIT = 80`（同文件 `:14`）与规格的 200 条不符，而 `buildDigest()` 的注释还写着"最多 200 条"。

**这条通道值不值这个位置？** 算术上不值：规则候选上限 8 条（`CANDIDATE_LIMIT`），模型最多再补 4 条，占候选列表不到三分之一；而这 4 条里唯一不是"规则换说法"的部分，是**跨 token 的短语**（`extractEntities()` 按非字母数字切词，切不出 `login bug`、`报表 v3` 这种片段）。一个只为"补短语"存在、要用户自己配端点、失败还要一行灰字的通道，撑不起一个设置分区。

## 3. 候选能力

顺序按问题本身排：先 AI（4 条），后规则（7 条）。规则条目不是凑数——如果一份候选清单里全是 AI，那它就是在给规则换说法。

### A1 · 手记草稿：一句带名词的话，可编辑

- **用户价值**：不写手记的人第一次得到"今天在改 dayfilm 的 EDL 时间码"这样一句话，改两个字就能存；写手记的人得到一个起头。
- **判定：AI。** 这是整份清单上唯一"规则做不到、且值得一次网络调用"的候选。
- **输入**：当天 `scenes`（标题在落盘前已过 `redactSample()`）+ `projects` + 时长；已有手记则作为下文语境。新增输入只有一个按钮。
- **落点**：hero 手记框（`#note`）下方一行草稿 + 「用这句」。点一下才写进 textarea 并立刻走 `saveNote()`；不点就不落盘，刷新即消失。**不进渲染路径**——海报 / 剧本 / PDF 只读 `notes.json`，模型输出现身之前必须先变成用户保存过的手记。
- **模板为什么做不到**：`judge()`（`rules.ts:31`）只吃 `(cutRate, longest)`，输出恒为"最长的一个镜头是 {exe} 的 N 分钟"；`pickNarration()`（`narration.ts:28`）五个分支只比 `scene.id`；`buildWeekVerdict()`（`week-film.ts:466`）只比三个数。一句带"EDL 时间码"的话，在整条通路上不存在，只能从标题的自然语言片段里读出来。按旧文档的判定线：删掉专有名词后剩下的部分 `judge()` 已经能生成，那它就是模板；这一句删掉名词什么都不剩，所以它是 AI。
- **它可能错在哪、会不会伤人**：会编因果（"因为要交稿所以……"）、编完成态（"修好了 EDL"其实只是打开了 issue）、编时间。兜底三条硬校验，任一不过整句丢弃、显示「没有可用的草稿」：① 句中每个专有名词必须是某条输入标题归一化后的子串；② 出现 `HH:MM` 必须在当天 `scenes` 里真实存在；③ 禁词表：因为 / 所以 / 终于 / 修好 / 搞定。长度 ≤120 字，落盘仍走 `clampNote()` 的 200 字上限。**注意一个代码事实**：手记是 600 ms 防抖自动保存的（`onNoteInput()` → `saveNote()`，`app.ts:1978-1989`），所以草稿**不能**直接写进 textarea，否则用户敲一个字符就自动落盘了；必须是"按钮插入 + 立即保存"这一次显式动作。
- **成本**：一次 30–70 条 `{exe, title, minutes}` ≈ 1.2–2k input token，输出 ≤150 token；云端 3–10 秒，本地 1.5B 20–60 秒（旧工程文档估算）；只在用户点的时候发。
- **工作量：M**（新 IPC + prompt + 校验 + 一处 UI；传输层直接复用 `src/main/ai/index.ts`）。

### A2 · 故事线命名：用你自己写过的词

- **用户价值**：候选现在给你的名字就是关键词本身（`storyCandidates()` 里 `name: term`），读起来像变量名（`login`、`df`）；换成"登录问题"这种给人看的名词，周主线和故事线矩阵才像剧情。
- **判定：AI**（只做命名，抽取仍是规则）。
- **输入**：候选的 term + 命中的 5 条样例标题 + 最近 30 天手记里出现过的词（优先复用用户自己的说法）。
- **落点**：设置「项目」候选行的名字输入框（已存在：`candidateRow()` 的 `candidate__name`，`app.ts:2706`），默认填入建议名，用户可改；点「添加」才写 `settings.projects`。
- **模板为什么做不到**：`storyCandidates()` 的 `name` 恒等于 `term`（`stories.ts:238`）；`candidateRow()` 只是把它填进 input。给"同一批镜头"起一个 ≤8 字的中文名是纯语言任务，规则最多做到首字母大写。
- **它可能错在哪、会不会伤人**：名字不参与匹配（`matchProject()` 只看 `terms`），编错了只是难看，改一下就好；重名已在 `addCandidate()` 里拦；term 沿用 `candidatesFrom()` 的真实命中计数，编不出不存在的词。伤害上限 = 一次改名。
- **成本**：8 个候选 × 5 条样例 ≈ 800–1000 token，输出 ≤8×10 字；2–5 秒；一次点击。
- **工作量：S**（复用 `ai-stories` 的形状，只换 prompt 与输出 schema）。

### A3 · 同义归并：把两条标题认成一件事（本清单风险最高）

- **用户价值**：`fix-login-bug.ts` 和 `DF-412 登录失败` 现在是两条线，用户得手写两个词，或者永远看不见这条线。
- **判定：AI。** 规则只能做子串归并（`storyCandidates()` 的去重只比"互为子串"）。
- **输入**：两个候选 + 各自 3–5 条样例标题。
- **落点**：设置「项目」里一行建议："这两条可能是一条：X / Y，示例…" + 「合并为一条」；合并 = 写一条带 2 个 terms 的规则（`ProjectRule.terms` 天然支持多词），名字由用户确认。
- **模板为什么做不到**：`extractEntities()` 用 `TOKEN_SPLIT` 按非字母数字切词，"登录"和 "login" 永远是两个实体，跨语言、近义表达在规则层面不可达。
- **它可能错在哪、会不会伤人**：**这是全场唯一会永久改统计的 AI 动作**——合并错了，周主线、故事线、精选全跟着错。兜底：一次只建议一对、必须展示双方样例、必须点确认、必须能一键删（`removeProject()` 已有）、顺序上把更具体的那条排前面因为 `matchProject()` 首命中即返回。我的判断：收益真实，但它是唯一"错了要用户自己排查数据"的项；如果 v4 只承受得起一次冒险，别选它——用户写两个词的成本远低于一次错并的排查成本。
- **成本**：一次 ≤500 token，2–4 秒；只应在用户点「找重复」时跑，最多 3 对。
- **工作量：M**（需要对候选两两配对的策略与证据渲染）。

### A4 · 检索 0 命中时的查询改写

- **用户价值**：搜"改时间码那会儿"能落到 `edl · dayfilm` 这类镜头，而不是一个空列表。
- **判定：AI**（只改写查询），召回与排序仍归 `searchScenes()`。
- **输入**：用户查询 + 该日期范围内的标题摘要（≤200 条）。**触发条件：现有 `searchScenes()` 返回 0 条**，才出现一个「换个说法找」按钮。
- **落点**：顶栏搜索框下一行"按「edl」「timecode」「时间码」再找一次"，点击后按改写词重跑，每条结果标出命中的是哪个词。只读，不落盘。
- **模板为什么做不到**：`searchScenes()`（`src/main/reel/search.ts:158`）是归一化后的 `includes` + 多词 AND；"改时间码"与 `edl` 之间没有任何字符串关系。别名表能覆盖 EDL↔时间码这类高频对，覆盖不了用户自己造的说法。
- **它可能错在哪、会不会伤人**：模型不产结果、不产日期、不排序；每个改写词必须在输入标题里真命中，否则丢弃（等同没改写）；结果仍为空就显示空，绝不"猜一个"。用户看到的是"按 X 找的"，可以改——这是唯一能识破错误的入口。
- **成本**：只在 0 命中时发；≈2–3k token，2–6 秒。
- **工作量：M**（新 IPC + 触发条件 + 命中理由渲染）。前置是下面 R7。

### R1 · 切断者：最长那条之后，你被什么接走

- **用户价值**：回答"我怎么更专注"里唯一能靠数据回答的那一半——不是你专注了多久，是**什么**在切你。例如"47 分钟那条之后，15 分钟里切了 6 次，4 次回到同一个标签页"。
- **判定：规则。**
- **输入**：当天 shots 的 `exe` / `title` / `start` / `end`。
- **落点**：hero 的「剪辑发现」第五类（`DISCOVERY_LABEL` 加一项、`findDiscoveries()` 加一个 `cutters`）；只在当天有 ≥30 分钟镜头时出现一条，证据 = 那几个镜头的 `start`，可点回胶片。文案只用时长、次数、窗口名，不出现"建议 / 应该 / 少"。
- **模板为什么做不到**：不是句子问题——`discover.ts` 现有的四类里，`return` 看实体重现、`switch` 看上午/下午主线、`revisit` 看同一标题、`late` 看时段，**没有一类看剪辑的落点**。缺的是关系，不是措辞。
- **它可能错在哪、会不会伤人**：纯本地计数，无幻觉。定义写死：以当天最长镜头为锚，统计它结束后 15 分钟内的镜头，按归一化标题计数，并列取更早。要注意语气——同一份事实写成"被切碎了"就变成了指责，所以只陈述、不评价，一天最多一条。
- **成本**：0；一次遍历镜头。
- **工作量：S**（`discover.ts` 一个函数 + `app.ts` 一行 label）。

### R2 · 上一集：上次停在这

- **用户价值**：打开今天先看到"上次：11/21 17:40 · dayfilm.ts · 42 分钟"，点一下跳到那天。跨天连续性，是日视图和周矩阵结构上都不给的东西。
- **判定：规则**（项目名或实体精确匹配，禁止模糊）。
- **输入**：今天时长第一的项目 / 实体；近 30 天 `scenes`（`suggestDays()` 已经打通这条读取通路）。
- **落点**：hero 一行（`#projectTotals` 之后），只读；点击 = `selectDay()` + `selectScene()`（两者已有）。
- **模板为什么做不到**：日视图只加载一天（`loadDate()`）；`matchProject()` 只在当天聚合；`week-film.ts` 最细到"天 + 主线"。跨天"同一实体最近一次出现"在现有任何函数里都不存在。
- **它可能错在哪、会不会伤人**：同名不同事。所以只显示日期、时间、原始标题、时长，让用户自己判断，不做"这个看起来是同一件事"的推断；**更不能用模型去做这层接续**——编造连续性是记录产品最不能犯的错，比"没有这一行"伤害大得多。精确匹配不上就不显示。
- **成本**：0；一次 30 天扫描，`DayCache` 有 LRU，多数命中缓存。
- **工作量：M**（新 IPC + hero 一行；仓库里任何新通道都是 5 个文件加测试的扇出）。

### R3 · 中场休息的形状

- **用户价值**：现在全产品只有一个"最长休息"数字（`longestRestSeconds()`，`app.ts:798`），不知道是哪一段、回来有没有回到原地。规则能说："12:10 离开 47 分钟，回来还是同一个窗口" / "19:40 离开，回来换成了 Chrome"。
- **判定：规则。**
- **输入**：`intermission` 镜头 + 它前后的两个 shot。
- **落点**：hero「剪辑发现」第六类 `break`，或贴在右栏"最长休息"那一行后面的一句（回来换了窗口）。只读。
- **模板为什么做不到**：`findDiscoveries()` 的 `featureShots()`（`discover.ts:47`）明确只收 `kind === 'shot'`，中场休息从不参与；`longestRestSeconds()` 只算长度，不看前后。
- **它可能错在哪、会不会伤人**：纯时间戳与 exe 比较，只有"同一窗口 / 不同窗口"两种结果，写不出第三种。
- **成本**：0。
- **工作量：S**。

### R4 · 三幕骨架

- **用户价值**：模型不可用时，hero 和剧本里仍有一句"上午 X · 下午 Y · 晚上 Z"（按当天两段最长中场休息切）；它同时也是 A1 的 prompt 输入，让模型不用自己找分段。
- **判定：规则。**
- **输入**：当天 `scenes`。
- **落点**：`renderScreenplay()` 的汇总段一行 + hero `#verdict` 下方（可选）；只读。
- **模板为什么做不到**：`judge()` 只有一句 note；`findSwitch()` 只有上午/下午两段，且要求两段各 ≥20 分钟才输出；没有"三段各在什么上"。
- **它可能错在哪、会不会伤人**：无。切分与主角都是本地计算。
- **成本**：0。
- **工作量：S**。

### R5 · 旁白的"第 N 次"

- **用户价值**：放映中段现在几乎每一镜都是"停留 N 分钟。"（`pickNarration()` 的 fallback，`narration.ts:52`）；改成"今天第 3 次回到这里，隔了 2 小时 10 分"，放映才像在讲这一天而不是在报时。
- **判定：规则。** 旧方案（`ai-brainstorm-product.md` C8）想让模型给"这个对象"命名，不需要——标题本身就是名字。
- **输入**：当天 shots 的归一化标题序列。
- **落点**：放映字幕 `#projectionSubtitleText`，只替换 fallback 分支；只读。
- **模板为什么做不到**：`pickNarration()` 的五个分支全靠 `scene.id` 与最长 / 首 / 尾 / 密集窗比较，没有"历史里出现过几次"这个输入。
- **它可能错在哪、会不会伤人**：无，纯计数。
- **成本**：0（每次切镜一次 O(n)）。
- **工作量：S**。

### R6 · 规则体检：谁吃掉了谁的镜头

- **用户价值**：`matchProject()` 首命中即返回（`src/shared/projects.ts:15`），第二条规则可能永远不生效，用户却以为它在工作。规则能一眼说明："这 12 个镜头被 3 条规则同时命中，最后归给了排在最前的 X"。
- **判定：规则。**
- **输入**：当天 `scenes` + `settings.projects`。
- **落点**：设置「项目」分区每行一条只读灰字（"命中 42 镜 · 与 Y 争 3 镜"），不新增面板、不新增区块。
- **模板为什么做不到**：现在没有任何地方展示"规则命中"本身，只有它进入统计后的结果（`totalByProject()` 只给最终归属）。信息一直在数据里，只是没人读。
- **它可能错在哪、会不会伤人**：无。这是解释，不是建议。
- **成本**：0。
- **工作量：S**（当天就能说明问题；要跨 7 天则 M）。

### R7 · 检索：时间词与范围对齐 + 命中理由

- **用户价值**：`parseQuery()` 已经认 `上上周`/`上周三`/`2月30日` 这一整套（`search.ts:53`），但 `src/main/index.ts:377` 只往检索里喂最近 7 天——**除了本周，这些时间词绝大多数情况下必然 0 命中**。用户以为"那天没发生过"，其实是被窗口裁掉了。修完再给每条结果补一行命中理由（"标题含 `edl`"），检索才有纠错入口。
- **判定：规则。**
- **输入**：查询 + `keptDays()` 里被时间词点名的日期（而不是固定 7 天）。
- **落点**：同一个搜索框与结果列表；每条加一行命中理由。可选的延伸：把 `notes.json` 也当第二语料（手记现在只写不读，只能一天一天翻），命中的日期作为一行结果。
- **模板为什么做不到**：不是语言问题，是范围口径与解释缺失。
- **它可能错在哪、会不会伤人**：无。
- **成本**：0（只读时间词点名的那几天）。
- **工作量：S**（范围 + 理由）/ **M**（手记进检索，要改返回形状与 IPC）。

## 4. 四个子问题

### a. 日评语 / 周评语换成模型，会更好吗？

不换，一分钱都不值。`judge()` 的 note 是**指认**不是点评：一句可核对的事实（"最长的一个镜头是 X 的 47 分钟"），而且它进剧本（`renderScreenplay()`）、PDF（`buildScriptHtml()`）、海报（`computePoster()` 只给它留两行）——三处都是会被保存、打印、给别人看的成品。`buildWeekVerdict()` 是三数对比加一张三行证据表，模型能加的只有措辞。

用户分辨得出来，而且分辨出来的方向是负的：模型版本会更长、更泛、形容词更多，正好撞在"海报只给这句留两行"的版式上。风险不是"不好看"，是**同一份数据两次导出会不一样**——"同一份数据任何时候渲染一致"写进 `PRODUCT.md`，ADR 0004 也明说不调用模型。

真正值一次调用的是**内容**而不是**评语**：一句带专有名词的话，把它落进用户自己的手记（A1），让渲染路径永远只读用户确认过的文字。这个差别是一句话：**评语说的是"这一天像什么"，数据已经答完了；摘要说的是"这一天在做什么"，我们一个字都还没答。**

### b. 不做 KPI 的前提下，"帮用户更专注"能落成什么？

三个形态，全部只读、全部带证据、全部不做趋势：

1. **回看时 · 切断者**（R1）：最长那条之后 15 分钟，你被什么接走了。这是"专注"里唯一能被数据回答的一半。
2. **回看时 · 中场休息的形状**（R3）：几点走的、走了多久、回来有没有回到原地。
3. **第二天早上 / 放映前 · 上一集**（R2）：昨天停在哪个窗口、停了多久。

必须砍掉的形态，以及为什么：

- **任何按天/周聚合的"专注时长""专注分""打断次数趋势"。** 一旦有指标就有目标；有目标用户就会为了让数字好看去改 `marks.json`——而标记是产品唯一的真实判断输入，污染它等于污染全部统计。
- **目标 / 承诺 / 连胜 / 番茄钟 / 通知提醒。** ADR 0004 已经把"专注承诺"和"主动提醒"划掉：这是观察工具，不是干预工具。
- **"你比上周更专注了"。** 需要基线、评价、因果，三样都不在数据里。
- **切断者排行榜（干扰源 Top 5）。** 榜单就是打分，只是换了个词。
- 补充一条：`idleMs` 的幅度（小于 60 秒的停顿）从来没被任何视图读过，原始 JSONL 里却完整保留着。**不要读它**——它能精确算出"你今天摸了多少次鱼"，那正是这个产品最不该有的能力。

### c. 把"检索窗口标题"升级成"问这一天 / 这一周"，值不值？

不做问答，做"问句 → 镜头列表"，而且要先修规则。`searchScenes()` 已经有多词 AND、时间词解析、标题归一化，缺的不是"理解"，是**范围**（钉死 7 天，`上上周` 永远查不到）和**解释**（说不清为什么这条命中）。值，因为"记不住标题原文"是真的痛；但值的部分九成在规则里，不在模型里。

输入是一句中文，输出就是现有列表 + 时间轴高亮 + 每行命中理由，落点是顶栏搜索框，不新开界面。模型的位置只有一个：**0 命中时**出现一次「换个说法找」，产 3 个候选词，结果仍然由真实 `includes` 产出，界面写明"按 X 找的"、可编辑、可清空。

防编造写成三条：模型不产结果、不产日期、不排序；每个改写词必须在输入标题里真命中，否则丢弃；空就是空，不许猜一个。不值得做的是向量索引（30 天、几千条标题，为"稍微聪明一点"付生产依赖 + 原生 ABI + 便携版解压 + 索引重建四笔债）和聊天框（一天几十个镜头，人读得过来；主语是版式，不是气泡）。

### d. 项目 / 故事线的自动化，模型还能帮什么？会不会丢控制权？

现在模型能给的只有 1 个词（`MAX_TERMS = 1`），且必须命中 ≥5 镜 / ≥10 分钟，还要和规则候选合并去重。它唯一不可替代的增量是**跨 token 的短语**与**一个更短的名字**——其余全是规则已经说过的话。

还能帮的三件事：命名（A2，安全）、同义归并（A3，危险，必须给出双方样例）、把用户手记里的词用作项目名（等于让项目说用户自己的语言）。

控制权靠四件事兜住，全部已在代码里：名字永远可改（`candidateRow()` 的 input）、词永远是可验证的子串（`candidatesFrom()` 在真实镜头里数命中）、不确认不落盘（`addCandidate()` 才写 `settings.projects`）、规则顺序由用户排——而顺序决定归属（`matchProject()` 首命中）。所以界线很清楚：**模型可以提议"这条线叫什么"，也可以提议"这两个词可能是一条线"（带样例、等确认）；不能决定归属、不能改顺序、不能删规则、不能一口气批量改。**

## 5. 推荐顺序

按用户价值 ÷ 工作量排，只给三条：

1. **R1 切断者（规则，S）** — 用户点名的"更专注"里唯一能靠数据回答的那一半；几十行、零模型、零网络，证据可点回镜头，做完当天就能说出一句以前说不出的话。
2. **R7 检索对齐（规则，S/M）** — 现在 `上上周` 这类时间词被 7 天窗口裁掉，等于承诺了却查不到；顺手补命中理由，那是用户唯一的纠错入口。
3. **A1 手记草稿（模型，M）** — 唯一值得花那次网络调用的地方，也是模型通道的存亡测试：如果 30 天真数据上它写不出带真名词的句子，就把通道收起来，别再为"补 1 个关键词"维护一个设置分区。

**如果 v4 只做一件事：R1。** 它是这份清单上唯一"用了数据里已经存在、但没人读的关系"、零风险、一个文件加一处 UI 的功能。如果预算只够模型那一半，那就是 A1，并且把它的失败当作模型通道的判决——不准就删，不要留一条永远在"候选"状态的功能。

## 6. 明确不建议做

1. **模型重写 `judge()` / `buildWeekVerdict()`** — 三处产物会被保存和打印，换模型只换来更长更泛、每次可能不同。
2. **打分 / 评级 / 趋势 / 目标 / 连胜 / 番茄钟** — 有目标就会有人为了数字改 `marks.json`，污染唯一的真实输入。
3. **模型逐镜打内容标签（旧 C2）** — 一天最多几十个唯一标题、每行 32px 且原文就在旁边，为可读性付几十次调用不划算。
4. **模型生成海报文案 / 片名 / 导演阐述 / 剧本开头** — 海报的表达力来自结构与数据，一句 slogan 会让它从证据退化成简历封面。
5. **模型判断正片 / 花絮** — 改的是 `featureMs` 与周主线，`SceneMark` 没有理由字段，错了无从追溯。
6. **模型自动写或覆盖手记** — `notes.json` 是产品里唯一的人声；机器写进去，这个功能就废了。草稿必须一次点击、必须人改。
7. **向量索引 / embedding 检索** — 30 天几千条标题，子串 + 时间词 + 别名够用；代价是四项工程债换"稍微聪明一点"。
8. **聊天式问答（"和这一天对话"）** — 一天几十个镜头，人读得过来；版式才是主语。
9. **用模型做"上一集"的模糊接续** — 同名不同事是记录产品最不能犯的错，比"没有这一行"伤害大得多。
10. **模型进渲染路径 / 进 `tick` / 进 `DayCache` / 进 HUD** — 每 2 秒一次广播的路径上不能有外部状态。
11. **AI 活动类型分布图 / 专注占比饼图** — `topApps` 只有 exe 维度，推不出活动类型；做出来就是 `PRODUCT.md` 明说不要的仪表盘。
12. **AI 朗读 / 配音** — 声音已经全部实时合成（放映音效），加 TTS 是另一个产品。
13. **默认开启 / 首启下载模型** — 便携版每次启动把整包解压到 `%TEMP%`，且与"默认零出站请求"正面冲突。

一句话收尾：这份数据最值钱的用法不是让模型多说两句，而是让我们**少说、准说**——先把剪辑落点、中场休息、跨天接续、规则归属这四处"已经在数据里但没人读"的关系读出来；模型只留在一处，把一天写成一句有人话名词的话，写进用户自己的 200 字里。
