# Dayfilm v4 执行计划

**裁决：选 C 的改良版（C+），按数据口径、跨天查询、当日叙事三个阶段推进，最后独立验收。**

不选 A，因为共享文件冲突几乎不可避免；不选 B，因为按层交付容易产生大量中间契约，而且数据层完成时无法直接验收用户可见功能。

原版 C 的问题是把「上一集」和「中场休息」放在一起，但前者涉及跨天数据与 IPC，后者只是当日数据的纯函数派生。两者没有真正的技术依赖。应该按技术依赖重新组合。

## 一、先冻结实现取舍

以下决定直接写入规格，不交给开发 Agent 二次裁决。

| 决策项        | 最终方案                            |
| ---------- | ------------------------------- |
| 上一集的数据来源   | 新增一个 `previousEpisode` IPC 通道   |
| 镜头之后 15 分钟 | 独立纯函数，展示在 `#discoveries` 内的固定位置 |
| 中场休息的形状    | 独立纯函数，展示在 hero 独立单行             |
| 命中理由       | 主进程返回，不在渲染层重算                   |
| cuts 兼容性   | 保留 `cuts` 总数，新增两个分类计数           |
| 数据持久化      | 完全不变                            |
| 现有发现算法     | 保持四类、最多三条的原有逻辑                  |

### 1. 上一集：新增 IPC，不复用 listDays + getDay

理由是 30 天的数据量虽然不大，但没有必要为了一条展示信息，把最多 29 个完整的 DayRollup 传给渲染层，还可能反复扰动 DayCache 的 LRU。

具体规则：

- 以当前所查看日期的最长镜头为匹配锚点。
- 匹配原始标题完全相同，或者命中同一个已定义项目；项目沿用现有规则及匹配优先级。
- 只查当前所查看日期之前的保留日期，从近到远查找，找到第一天即停止；当天有多次匹配时取最后一次。
- 复用主进程现有的 DayCache 读取路径，逐日查询，不批量预热、不扩大缓存容量。
- 只返回日期、镜头起始时刻、原始标题、时长及匹配类型。无匹配返回空值。
- 仅在切换日期、匹配锚点或相关规则发生变化时重新查询，不跟随每两秒采样重复查询。

### 2. 两个当日派生功能：不进入 findDiscoveries 的候选池

新增 `src/renderer/src/lib/day-insights.ts`，包含两个独立纯函数。

**镜头之后 15 分钟：**

以现有 `longestShot` 为基准，取其结束时刻之后的半开区间，即包含结束时刻、不包含第 15 分钟的结束边界。统计在此区间内开始的有效镜头，按归一化标题分组、按镜头出现次数计数，不统计采样次数，不统计休息。

按次数降序、首次出现时间升序排列，展示前三个窗口。没有后续镜头则不展示。

**中场休息的形状：**

复用现有休息区间，选择最长的一段；等长时取最早的一段。比较休息之前与返回之后的有效窗口身份，即 exe 和 title，而不是仅比较应用名。

没有记录到返回窗口时，显示「尚未记录返回」，不推断用户仍在休息。

### 3. 命中理由：直接修改 search 返回契约

采用结果对象，而不是单纯的数组。

| 返回字段            | 用途                 |
| --------------- | ------------------ |
| `hits`          | 命中结果集合             |
| `hits[].scene`  | 原有镜头结果，保留已有日期及定位信息 |
| `hits[].reason` | 实际命中的文本词、明确命中的日期   |
| `coverage`      | 完整覆盖、部分覆盖、保留范围外    |
| `retainedFrom`  | 实际保留范围起始日期         |

`reason` 返回结构化信息，中文文案由渲染层格式化。匹配与命中理由必须出自同一次判断，不能在 renderer 再实现一次搜索算法。

时间范围优先级固定为：

**明确时间词指定范围 → 与保留范围取交集 → 查询数据。**

没有时间词时，继续沿用最近七天。保留范围使用存储层实际的清理规则，而不是写死 30 天或根据最早存在的文件推断。

### P1 — 数据口径与缺陷修复

**负责人：数据基础 Agent**

范围：① 锁屏误报 + ② cuts 拆分。

#### 实现顺序

先修复采样，再统一窗口判定，最后拆分计数。

锁屏修复：

- `GetForegroundWindow()` 返回 0 时，输出合法采样，exe 和 title 均为空。
- 使用两个空字段作为持久化的 away 判定依据，不新增 JSONL 字段，也不伪造 idleMs。
- 主进程正常接收该采样、清除采集错误状态。
- away 采样立即进入休息分支，不等待普通 idle 的 60 秒门槛，不生成有效镜头。
- 真正的 PowerShell 异常、损坏数据仍按采集错误处理。

cuts 拆分：

- 跨应用：相邻有效窗口的 exe 不同。
- 应用内：exe 相同、title 不同。
- 窗口相同：不产生剪辑。
- `cuts = appCuts + withinAppCuts`。

三个位置统一复用同一个窗口身份与切换判定函数。题材继续使用 cuts 总数及原有计算口径、四档边界。新分类字段绝不作为镜头切分依据。

away 不参与剪辑计数，也不人为连接其前后的窗口产生剪辑；其他原有休息、短镜头和标记的统计规则保持不变。

## 三、最容易写错的三个点

### 风险 1：三条数据路径产生不同的电影

**严重程度：最高。**

`groupRuns`、\`aggregate.append\`、\`liveScene\` 很容易只改对其中两处。表现是实时界面正常，但重启或者切换日期后，镜头数量和题材突然变化。

锁屏修复也容易出现同类问题：全量聚合认识 away，实时镜头却把空标题当成新窗口。

**兜底测试：三路径等价性测试。**

使用同一份人工构造的采样序列：

各有效窗口段均满足镜头时长门槛；锁屏不产生额外剪辑。

同时通过全量、逐条增量、实时处理三个入口，比较有效镜头边界、两个 cuts 子计数、休息区间及最终题材。

测试落点：\`aggregate.test.ts\`、\`pipeline.test.ts\`。

### 风险 2：搜索解析正确，但数据根本没有进入搜索函数

现有问题就是这个类型。单测可能证明 `parseQuery` 能认出「上周三」，也能证明 `searchScenes` 正确匹配，但生产环境仍然只加载七天数据。

**兜底测试：IPC 端到端范围测试。**

固定当前日期为 2026 年 11 月 27 日，保留期为 30 个自然日，包含当天：

| 测试日期      | 预期行为        |
| --------- | ----------- |

### 风险 3：派生功能把推断当成事实

最典型的错误是上一集查到了所选日期之后的镜头，或者休息之后回到同一个应用、不同文档，却显示「回到了原来的窗口」。

15 分钟观察也容易误用采样次数，把持续时间很长的窗口显示为出现了几十次。

**兜底测试：反例优先。**

| 功能   | 必须通过的反例                       |

| 中场休息 | 没有返回证据，不判定是否回到原窗口             |
