我在给 Dayfilm 设计"与 AI 结合"的功能，需要你裁决方向与形态。

产品：Windows 桌面应用（Electron + TypeScript，本地优先），每 2 秒记录一次前台窗口，把一天剪成一部"电影"：连续待在同一窗口 = 一个镜头，切换窗口 = 一次剪辑，离开 >60 秒 = 中场休息；由剪辑密度推出当天"题材"（长镜头 / 标准剪辑 / 快切 / 跳切风暴）。已实现（v2.6）：竖向胶片时间轴（每 5 分钟一帧）、16:9 放映态（随镜头切换的旁白字幕 + 实时合成音效）、镜头表与近 7 天标题/进程检索、项目规则（把镜头归到"故事线"）、导演手记（每天一句）、正片/花絮标记、周电影（七日叙事弧 + 周评语 + 本周精选）、片场日历、双日对比、置顶导演 HUD、导出 Markdown 剧本 / CMX3600 EDL / PDF / 1600×1000 海报。

数据事实（已核实）：每条采样只有 4 个字段——时间戳、前台进程名（Code、WindowsTerminal、msedge、WINWORD 之类）、窗口标题（截断 512 字，例如 "fix-login-bug.ts - dayfilm - Visual Studio Code"、"[DF-412] 登录失败 · PR #88 · GitHub"、"ACME 项目周会 - 腾讯会议"、"张三 - 微信"）、距最后一次输入的空闲毫秒。不截屏、不记键盘、不联网。标题里其实塞满了文件名、issue 号、PR 标题、文档名、会议名、聊天对象名。

约束（不可让渡）：不联网（CSP 只允许本地资源，启动即禁止站外请求）、数据只在本机、确定性（同一份数据任何时间渲染结果一致）、品牌是冷静克制的"剪辑台/放映室"，不是效率仪表盘；历史外部裁决已明确否决过"周报式"和"效率管理工具"方向。

现状证据（所以"AI 结合"目前是零）：所有"智能"文字都是模板——judge() 只有 4 档 label 加一句 note；放映旁白是按 5 条优先级规则拼出的固定句式；周评语同一模板；项目归属是子串匹配，要用户手写关键词；检索是 title/exe 的 includes() 子串匹配，只覆盖最近 7 天。

摆在我面前的三种落地形态：
A. 本地生成式模型（node-llama-cpp + 1–3B GGUF）：能写真文字，代价是新增原生依赖、便携版 exe 从几十 MB 涨到 GB 级（或首启下载模型）、8GB 内存办公机的延迟与 OOM 风险。
B. 用户自带云端 API key（显式开启）：文字质量最好，但破坏"不联网"这条产品承诺，要改文档、UI 措辞与安全边界。
C. 完全不用模型：本地统计/NLP（标题实体抽取、字符 n-gram TF-IDF 余弦、字典与聚类、规则检测器），输出可计算、可测试、确定性，但写不出"像影评的句子"。

六个候选功能：
1. 从窗口标题自动归纳项目/故事线，生成用户可直接接受的规则（现在要用户手写关键词）。
2. 给每个镜头归类活动类型（编码 / 写作 / 沟通 / 会议 / 阅读 / 终端），周视图改按类型讲主线。
3. 自然语言检索：把"上周三我在改哪个 PDF 那件事"变成结构化过滤加语义匹配。
4. AI 写导演评语 / 手记草稿 / 旁白（替换或叠加现有模板）。
5. AI 边检测边叙述：规则检测器（深夜工作、连续 3 小时不休、会议超时、频繁切换）负责找事实，AI 只负责说一句带证据的话。
6. 隐私向：扫描标题里像人名 / 账号 / 客户名的词，建议脱敏关键词。

我的倾向：C 打底，先做 5，其次 1；4 排最后，且绝不能替换确定性口径。但我不确定：用户想要的"AI 感"能不能靠 C 满足，还是必须有一次真正的生成式输出才能让人觉得这软件会思考。

问题：形态选哪个（A / B / C 或组合）？六个里先做哪两个、顺序如何？每个的形态要怎么改才不算堆功能？请特别回答：如果坚持不联网，C 能走到什么程度、它的天花板在哪；以及 4 这类"AI 文采"对这款产品是加分还是毒药。

只给结论、理由和下一步；不要过度工程设计，不要防御性免责表述。
