# Dayfilm 该加哪些 AI 功能：四方裁决与建议

三份头脑风暴（产品 / 工程 / 怀疑论）加一次外部裁决（ChatGPT），在真实数据上跑了一次标题探针。结论和理由都在这里；过程材料是 `ai-brainstorm-product.md`、`ai-brainstorm-engineering.md`、`ai-brainstorm-skeptic.md`、`gpt-answer-9.md`。

## 0. 结论

1. **现在该做的不是"AI 功能"，是"故事线候选"**：从窗口标题里抽出可验证的名词，给用户一份带证据的 `settings.projects` 草稿，勾选才生效。零模型、零联网、零体积，四方一致同意这是第一位。
2. **生成式文字不进入主界面**。现有 `judge()` / `buildWeekVerdict` / `pickNarration` 已经把"怎么说"做到模板上限；换模型只会让同一份数据每次说出不同的句子，直接违背 `PRODUCT.md` 的确定性承诺（外部裁决原话：**"放在核心体验里是毒药"**）。
3. **模型唯一合法的位置是"用户显式点一下"的旁路**，且默认关闭、不入包、不常驻。要不要做，等第 4 节的探针回答"规则抽不出名词是不是真的"之后再定。

## 1. 四方裁决对照

| 判断 | 产品 | 工程 | 怀疑论 | ChatGPT | 收敛 |
| --- | --- | --- | --- | --- | --- |
| 云端 BYO key | 不做 | 不做 | 不做 | 否决 | **四方一致否决** |
| 本地 GGUF / Ollama | opt-in 旁路 | opt-in 旁路（Ollama 质量/成本最优） | 默认关，且模型不许进渲染路径 | 以后再说，独立安装 | 一致：只作旁路 |
| 替换 `judge()` / 周评语 | 不做 | 不做（R1 收敛口径≠重写） | 拒绝 | 毒药 | **一致否决** |
| 从标题抽名词做项目规则 | C3，做 | R2，做（7 成是字符串工程） | 做，但必须"候选+确认" | 第一位 | **一致：第一位** |
| 事件检测/剪辑发现 | 作为 C1 的证据层 | 规则检测器可行 | 可以，但别变成效率警告 | 第二位 | 一致：第二位 |
| 语义/自然语言检索 | 先不做 | 先做归一化 + TF-IDF | 做，但输出列表不是对话 | 第三位，改名"找回某一幕" | 分歧仅在"要不要向量"：先不 |
| 活动类型分类 | 只作句子里的一个词槽 | exe 白名单能覆盖 3–4 类 | 自动打标签必错 | 降级为可选标签 | 一致：不单独做成分布图 |
| AI 写评语/片名/海报文案 | 排最后 | 与确定性冲突 | 全部拒绝 | 拒绝 | **一致否决** |
| 脱敏建议 | 不主张 | 不主张 | 唯一真机会 | 未提 | 待定，见第 3.4 节 |

唯一的实质分歧：**"模型是不是必需品"**。产品侧认为句子里没有一个名词来自标题，规则抽不出来；工程与怀疑论认为七成是字符串工程。这不是观点问题，可以测——第 4 节。

## 2. 真实数据探针（本地 2 天，只算聚合）

`%APPDATA%\dayfilm\days` 现有 2 天、36,801 条采样、**70 个不同的 `(exe, title)` 对**：

| 指标 | 值 |
| --- | --- |
| 不同标题对 / 归一化后 | 70 / 59 |
| 空标题 | 4（5.7%） |
| `[已隐藏]` | 1（1.4%） |
| 纯应用名（无内容） | 3（4.3%） |
| 含 issue/PR 号 | 0（0%） |
| 含文件名/文档名 | 12（17.1%） |
| 短标题（≤6 字） | 10（14.3%） |
| 最高频标题 | `ChatGPT - not-my-app - 个人`（23,121 条采样，占 63%） |

三条结论：

1. **一天的不同窗口只有几十个，不是几千个。** 38,000 条采样里只有约 30 个不同标题。这意味着实体层和规则候选的计算量可以忽略，也让"人工确认候选"在 UI 上真的可行（列表是 20 行量级，不是 200 行）。
2. **标题的语义密度取决于工种，而且头号窗口占掉大半时间。** 这份数据的 63% 落在同一个 ChatGPT 标签页里——**这个窗口内部发生了什么，数据完全不知道**。任何"活动类型分布""今天在干什么"的推断在这份数据上都会编。
3. **17% 的标题带可用文件名，0% 带 issue 号。** 这是两天、单机、偏聊天/浏览的使用；开发者典型日（Code + Terminal + GitHub）会更高，但**不能假设稳定过半**。这条数字是第 4 节探针的门槛依据。

取证脚本：`%TEMP%\dayfilm-title-probe.mjs`（一次性，未入库）。

## 3. 建议做（按顺序，每项都能独立交付）

### 3.1 故事线候选（第一位，四方一致）

- **一句话**：设置里的"从最近 30 天找候选故事线"——列出 `login`（42 镜 / 1 小时 12 分 / 例：`fix-login-bug · VS Code`），勾一个词、填一个名字，才写成 `settings.projects` 的一条规则。
- **为什么规则做不到**：`matchProject()` 是"关键词 → 名字"的子串匹配（`src/shared/projects.ts`），**关键词必须由用户先想到**。没有规则时周主线退化成 exe 名（`week-film.ts` 的 `mainLineOf`）。这是产品里唯一"用户知道有这条线，但写不出词"的位置。
- **形态（怀疑论的硬约束）**：只出草稿、必须确认、可撤销；候选永远带命中标题原文；空候选就不显示入口；不静默写入。
- **实现**（工程 R2）：纯函数，`src/shared/` 里加一个 `suggest.ts`，做归一化（去 ` - App` 后缀、去未读计数、去路径前缀、全半角）+ 频次/共现统计；7 天 × 几十个标题，10 ms 级。零依赖。
- **验收**：草稿被接受率（> 1/3 才值得保留入口）；误合并数（同一个词命中两个不同项目名 = 失败）；拒绝后 `buildWeekFilm` 立刻回到旧主线。
- **不做会怎样**：周电影继续按进程名讲主线，`PROJECT.md` 里的"故事线"对大多数用户是空功能。

### 3.2 剪辑发现（第二位）

- **一句话**：在镜头表和 hero 上给 1–3 条高置信度事件——"重返主线""主线易位""同一文件被反复打开""最长镜头出现在深夜"，每条都能点回镜头。
- **为什么规则做不到**：现在的 `judge()` 只有"最长镜头 + 剪辑率"（`rules.ts`），`pickHighlights()` 只有最长/最密/最长进程（`highlights.ts`）；**没有"跨时间的关系"**——A 上午出现、下午又出现，这件事数据结构里不存在。
- **形态**：检测器是规则（可测），命名是模板（可测）；**没人可看就不显示**；不做通知、不打分、不输出"建议你少切换"。
- **验收**：每条发现的证据镜头数 ≤ 5、全部可定位；误报率（用户点开说"这不算"）< 20%；一天最多 3 条。
- **注意**：`docs/delegate/gpt-answer-9.md` 的原话是"描述可观察的行为，不推断心理"——所有文案的谓语只允许时长、次数、窗口名。

### 3.3 找回某一幕（第三位，先做确定性版）

- **一句话**：现有搜索框接受"上周三 那个 pdf"，返回**镜头列表 + 时间轴高亮**，每条写清命中依据。
- **为什么规则做不到**：`searchScenes()` 是 `title.includes(query)` 且只覆盖最近 7 天（`src/main/index.ts` 的 `SEARCH_DAYS = 7`，`reel/index.ts`）；用户记不住标题原文。
- **形态**：不做对话、不做问答；先做归一化 + 别名 + 多词 AND + 时间词解析；**命中原因说不清的结果不显示**。
- **验收**：20 条真实查询的 0 命中率 < 15% 才继续；否则先修归一化，不上向量。
- **备注**：怀疑论认为 6000 个镜头、几 MB 文本，确定性够了；产品侧同意"先测再谈 embedding"。两方唯一的差别是门槛数字，第 4 节统一。

### 3.4 脱敏建议（独立小项，待定）

- **一句话**：扫描标题里像人名 / 客户名 / 账号 / 内部代号的词，建议成 `settings.redactTerms` 的候选，勾选才写入。
- **为什么值得单列**：`BUILTIN_REDACT_TERMS` 是黑名单，永远列不全（`src/shared/settings.ts`）；这是现有规则的真实缺口，而"建议 + 确认"不动渲染、不占表达位。
- **为什么待定**：它需要判断"一个词像不像敏感信息"，这正是规则最弱、模型最明显更强的地方 —— 但也是唯一一个**必须看到标题原文才能判断**的功能。要么接受本地模型，要么接受"只按模式匹配（邮箱、手机号、URL token、`*_内部`）"，后者便宜且零风险。**建议先做模式匹配版**，模型版留到有本地推理通道之后。

## 4. 先做探针，再决定要不要模型

四方对"要不要模型"的分歧，可以用一次探针收敛。**在写任何模型代码之前**：

1. 用 30 天真实数据，跑 3.1 的归一化 + 实体抽取，统计：**能抽出可用名词的不同标题占比**、**能形成 ≥5 镜关联的候选故事线数**。
2. 门槛：可用名词覆盖率 ≥ 40%，或每周能形成 ≥ 3 条候选故事线 → **不需要模型**，3.1 直接交付。
3. 低于门槛，且在真实标题上人工看得出"明明是一件事却抽不出来"（例如"登录失败" vs "认证异常"）→ 才考虑 opt-in 模型，且只用来**补实体归并**，不用来写句子。
4. 现在这 2 天数据的先验：17.1% 带文件名、0% issue 号、63% 时间在一个窗口里。**这份样本倾向于"不需要模型"**，但样本只有两天、偏聊天浏览，不能当结论。

工程侧已经把模型的代价测清了（`ai-brainstorm-engineering.md`）：1.5B Q4 在 8 GB 机上单次 13–23 秒（估算）、常驻 RSS 已用 249–254 MB / 预算 300 MB、便携版每次启动解压整包 —— 所以模型必须是"按需起的独立子进程 + 用户自备 `.gguf`"，绝不会是默认路径。

## 5. 明确不做

| 不做 | 一句话理由 |
| --- | --- |
| 云端 API key | 与"不联网 / 数据只在本机"正面冲突；主进程的 `fetch` 不受现有网络守卫约束（守卫是 session 级），等于拿旧文案骗用户。 |
| 截图 / 多模态 | 产品第一句是"不采集屏幕内容"；截图会把刚脱敏的标题重新变成原文。 |
| AI 重写 `judge()` / 周评语 / 旁白 | 三处模板已经是"取最大事实 + 带证据"的最优解；换模型只变长变泛，且每次渲染可能不同。 |
| 活动类型饼图 / 效率评分 / 情绪判读 | 数据只有窗口标题，头号窗口内部无信息（探针：63% 时间在同一个标签页）；这类输出会被用户当真。 |
| AI 周报 / 月度回顾长文 | ADR 0004 已否决"七天相加可得"；为分享优化会把目标读者换成第三方。 |
| 自动写手记 / 自动改标记 / 自动建项目 | `notes.json` 是产品里唯一的人声；`marks` / `projects` 是用户的判断，写错就直接改统计。 |
| 聊天式问答（"和这一天对话"） | 主语是版式不是气泡；一天几十个镜头，人读得过来。 |
| 首启下载模型 / 模型入包 | 与"不联网"冲突，便携版每次启动把整包解压到 `%TEMP%`，加 1 GB 是灾难。 |

## 6. 需要你定的一件事

外部裁决最后一句是：**连"AI 功能"这个产品入口都不要做**，让能力长成现有名词——"发现故事线""剪辑发现""找回某一幕"。这决定了两件事：

- **要不要在 UI 和文案里出现"AI"字样**。不出现：3.1–3.3 就是三个普通功能，`PRODUCT.md` 一个字不用改。出现：必须写清"模型在本机跑、与联网无关"，并接受用户把"AI"自动等同于联网的误解。
- **要不要现在就规划 opt-in 本地模型出口**（`ai` 设置项 + 一个 IPC 通道 + `comments.json` 式的冻结产物）。规划了，未来接 Ollama / 自备 `.gguf` 不用返工；不规划，第 4 节探针若判定需要模型，再补契约要多动 5 个文件（`ipc.ts` / `ipc/index.ts` / `main/index.ts` / `preload` / `ipc.test.ts`）。

我的建议：**先按"不出现 AI 字样"交付 3.1 + 3.2，把模型出口留成一个不做进默认路径的内部接口**；等真实用户在被接受的候选故事线上提出"能不能说得更像人话"，再谈第 4 步。
